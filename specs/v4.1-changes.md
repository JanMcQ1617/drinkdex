## 1. The onboarding flow

### 1.1 Where it is drawn

**`src/components/FirstRun.tsx`** (new) is an absolute-fill overlay mounted in `src/app/_layout.tsx` straight after `</Stack>`. So `PasswordResetOverlay`, `CelebrationOverlay` and `VideoIntro` all draw above it, and the cold-start film plays first.

**It is visible when all of these hold:**

- `useAuth.ready`;
- `!useAuth.session`;
- `useTaste.hydrated`;
- `!useTaste.done`;
- `!useTaste.signInFirst`.

While visible it is `accessibilityViewIsModal`, on `colors.bg`, with its own safe-area insets. It covers the tab bar, so nothing under it can be swiped or tapped.

It renders `<OnboardingFlow mode="first-run" onExit={…} />`. The `onExit` reasons:

| `onExit(reason)` | What FirstRun does |
|---|---|
| `'signin'` ("I already have an account") | `useTaste.getState().chooseSignIn()` (memory only), then `router.navigate('/')`. The Home tab's AuthGate shows WelcomeBack or the ways in, exactly as today. The next cold start shows the welcome again. |
| `'handoff'` (on the sign-in step, the person chose email or phone, so `useSignInFlow.step` left `'entry'`) | `finish()`, then `router.navigate('/')`. The Home gate is already on that step (the flow store is shared), so the person carries on there. |
| `'not-now'` | `finish()`. The Home gate shows the ways in under the person's picks (§1.6). |
| a session arrives | Nothing to do. The overlay hides itself (`!session`), and the taste store sets `done` (§3.2). |

The old in-gate taste picker is retired: `auth/TastePicker.tsx` is deleted. In `store/signInFlow`, the `'tastes'` step, `picks`, `joined`, `togglePick`, `continueTastes`, `signInFromTastes`, `backToTastes`, `applyPicks` and its `useCollection.subscribe` all go. The flow's initial step becomes `'entry'`. The old picks seeded the Dex; nothing seeds the Dex any more.

**Progress.** The path is the steps from `hello` to `allset` that apply (`followup`, `bar` and `heard` are conditional).

- Longest path: **12 steps**. Shortest: **10** (no follow-up, no bar). With `ASK_HEARD_FROM` on, one more.
- The bar shows `index / path.length`, where `hello` is 1. So `allset` and `signin` are full.
- VoiceOver reads "Step k of N". N is recomputed whenever an answer changes the path, and the fill re-times to it (m11).
- `welcome` and `underage` show no top bar.
- The top bar is the back chevron, the progress rule and Skip. Back on `hello` returns to the welcome, mirrored; on `signin` it returns to `allset`. Skip appears only where the table says.
- Skip on a question records `null` (or `[]` for a multi), then pushes. On `dexintro`, Skip pushes.

**Back.** Back returns along the current path, mirrored (m1). It never returns to `age` from `dexintro`: Back on `dexintro` goes to `hello`, and the age answer stands.

- Changing `spirits` recomputes `styleOf`. A follow-up whose spirit was unticked is dropped from the path and its `styles` are cleared.
- Changing `home` to never (or Skip) drops `bar`. Its ticks are not written.

**Resume.** `useTaste.step` is persisted. A cold start resumes at that step only while `ageOk`; otherwise it starts at `welcome`. `pour` resumes as `results`, with the stored `picks`.

### 1.3 Retake mode (Settings → Your tastes)

`<OnboardingFlow mode="retake" onExit={…} />`:

- **Path:** `usually → spirits → followup? → flavours → home → bar? → pour → results`. It starts from the stored answers, pre-selected.
- No welcome, hello, age, dexintro, allset or sign-in. Their accounts already confirmed their age.
- On the first step the back chevron is a **close** glyph, labelled "Close", which gives `onExit('closed')` and keeps the old answers.
- On `results` the key reads **Done** and gives `onExit('done')`. Answers are written as each step is left, so closing midway keeps the steps already passed. That is acceptable, and it is the same as first-run.
- The progress count is the retake path's length.
- The bar step pre-ticks rows already in My Bar as well as the defaults, and Continue only **adds**. It never removes a bottle from My Bar.

### 1.5 Under-age, including the "I already have an account" bypass (spec §11)

- **No** → `refuseAge(now)`:
  - `underAgeUntil = now + 24 h`;
  - `ageOk = false`;
  - answers, picks and `step` reset to empty;
  - `saved` is kept (it predates this run);
  - shows `underage`.
- **Back to start** → `welcome`. While `underAgeActive()`, **Get started** opens `underage` again. The copy never mentions the 24 h or a way round it.
- **"I already have an account" still signs in an existing account.** A **brand-new** account made inside the lock is refused in `AuthGate`:
  - The test: `ownProfile && isPlaceholderUsername(ownProfile.username) && underAgeActive()`.
  - Instead of `ChooseUsername`, it renders `<UnderAgeStop busy={…} onBack={…} />`, exported by the onboarding package. That is the `underage` screen's body, with the key "Back to start".
  - The key runs `useAuth.getState().deleteAccount()`. That does the Apple revoke and `delete_own_account()`, and a user gesture is needed for Apple's sheet. If it returns false (Apple sheet closed, or offline), it runs `signOut()` instead.
  - Either way the person lands on the signed-out app. FirstRun shows the welcome, and Get started shows `underage`.
  - A placeholder account left behind by a failed delete meets the same screen on every launch until the lock ends. After that it reaches `ChooseUsername` as normal.
  - Account deletion clears the taste store **except `underAgeUntil`** (§3.2).

### 1.7 Motion

Spec §7 applies in full: m1 to m23, measured from Imprint, with these rules.

**Rules:**

- **Never invisible.** Incoming content starts at opacity **0.6** and 8 pt off its rest.
- **JS clocks.** Every stagger, auto-advance, outgoing-layer removal and reveal phase runs on a JS `setTimeout`.
- **JS end states.** Every animated control gets a JS end-state re-render at duration + 50 ms, drawn with plain styles. A Release Reanimated stall therefore cannot blank or freeze a control: a pick still turns ink, Continue still turns ink, a tick still shows its check.
- **Reduce Motion** (`useReducedMotion()`): every duration 0, no swell, breathing, drift or pop. The reveal becomes a 300 ms crossfade, and the auto-advance delays stay.
- **VoiceOver or Switch Control:** no auto-advance. Single-choice and narration screens show an enabled Continue.

**Changes from the spec:**

- The friends narration (m16) is not built.
- The welcome-key slide (m2) still applies: `welcome → hello` is the first push.
- RN `Animated` is **not** used for timed motion (check-design rule 15). Use Reanimated shared values. Spec §7.0's "or RN Animated with useNativeDriver" is withdrawn.
- **Haptics** (spec §7.3) go through `haptic` in `components/ui.tsx`: light on a pick, medium when m20 resolves, success on All set.

## 2. Recommendations: the port

### 2.1 Files

- **`src/lib/recommendCore.ts`.** A line-for-line TypeScript port of `specs/v4-onboarding/tools/recommend.mjs`:
  - `SPIRITS`, `STYLES`, `FLAVOURS`, `abvOf`, `baseSpirit`, `spiritHits`, `flavourHit`, `missingCount`, `score`, `familyKey`, `shareKey`, `whyLine`, `recommend`, `matchingCount`, `makeableCount`, `barRows`, `PICKS = 6`;
  - plus `collage(answers, n)`, the CLI's collage logic generalised. It takes photographed drinks from the scored pool, best first, and tops up from the known list when it has fewer than `n`.
  - **No runtime imports** (`import type` only). It exports `createRecommender(data)`, which closes over `{ drinks, ingredients, recipes, photoIds: ReadonlySet<string>, knownIds: readonly string[] }`, so a Node script can run it.
  - The bar logic is the **reference's** exact-id `missingCount`, not `lib/bar`'s generic-expanding `matchBar`, so the picks and `makeNow` match the reference bit for bit.
- **`src/lib/recommend.ts`.** It binds the core to the app's data:
  - `DRINKS` from `@/data` (already sorted by Dex number; the reference sorts its pool with a Dex-number tie-break, so the order is the same);
  - the ingredients and recipes from `@/data/barIndex.json`;
  - `photoIds` = the ids `photoFor()` resolves;
  - `knownIds` = `FIRST_TASTE_IDS` from `lib/tastes`.
  - It re-exports everything, plus the types in §3.1, and memoises `recommend` on `(answers, bar owned, Dex unlock ids)` identity. The Dex ids are the `exclude` set.
- **`src/lib/tastes.ts`.** Add `export const FIRST_TASTE_IDS: readonly string[] = IDS;`. Keep the literal `const IDS = [` exactly as it is, because the reference script reads it by regex. Keep every existing export (`latestDexIds` is used by `log.tsx`).
- **`scripts/check-recommend.mjs`** (new; the unit test, since there is no Jest):
  - It transpiles `src/lib/recommendCore.ts` with the project's own `typescript` (`ts.transpileModule`, ESM output) and imports it from a data URL.
  - It feeds it the same JSON and photo set that `recommend.mjs` reads, and imports the reference's exports.
  - It asserts that runs **A to D** (spec §5.6 answers) give the reference's ids, order, `why`, `makeNow` and `score`, plus `matchingCount` 574, 149, 2073 and 378 and the reference's `barRows`.
  - It then sweeps **2,000 deterministic answer combinations** (a seeded LCG over every field, with goal fixed to null and to each value) and diffs core against reference. It prints every mismatch and exits 1 on any.
  - `node scripts/check-recommend.mjs` must print a pass.

**The pinned API of `@/lib/recommend`.** The onboarding package codes against it:

```ts

}
```

**Persistence.** It uses `persist` with `createGuardedStorage()` under the name **`sipply-taste.v1`**. `partialize` leaves out `hydrated` and `signInFirst`. `hydrated` is set in `merge`, as in `store/bar.ts`. On read, ids that `getDrink` no longer knows are dropped from `picks` and `saved`.

### 3.2 Store behaviour, at the module's foot (as `store/signInFlow` does)

**When a session arrives** (`useAuth.subscribe`, signed-out → signed-in):

1. `done = true`, `step = 'welcome'`, `signInFirst = false`.
2. If `syncedFor !== null && syncedFor !== uid`, the local answers, picks and saved belong to another account. Clear them (keep `underAgeUntil`) before syncing.
3. Then run the sync (§3.4).

**Sign-out** keeps everything (it is the phone's), and `syncedFor` stays.

**Account deletion** (`onAccountDeleted` from `store/auth`) resets to the initial state **except `underAgeUntil`**. `done` returns to false, so the welcome shows.

**Pruning.** `useCollection.subscribe`: any drink id newly in `unlocks` is removed from `saved`.

### 3.4 Sync (in `src/store/taste.ts`, using `@/lib/supabase`)

- **When it runs:** on session arrival, and on hydrate if a session is already there.
  1. Select the account's `taste_profiles` row, and `want_to_try` ordered by `created_at desc`.
  2. **Answers:** if the server row exists with a non-empty `answers` that has `v: 1`, the server wins locally. Otherwise, if `hasAnswers(local)`, upsert the local copy (with `heard_from` when non-null).
  3. **Saved:** the union, with the server's order first and local-only ids after. Insert the local-only ids, then set `syncedFor = uid`.
- **After that, while signed in:** changes to `answers`, `heardFrom` and `saved` are pushed **debounced 2 s**. Answers are an upsert. Saved diffs against the last synced set: insert new ids, delete removed ones. A `want_to_try_full` refusal is ignored, because the local cap matches.
- **022 not applied** (PGRST205, 42P01, or a "relation does not exist" message): mark it unsupported for this runtime and keep the local copy. Nothing shows an error, and the next launch tries again.
- **Never** sent while signed out. Nothing is sent before an account exists.
